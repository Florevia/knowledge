## 90 秒项目介绍

这是一个面向海外用户的移动小说 H5。我基于 Nuxt 4 做了公开内容 SSR、私有页面 CSR 的混合架构，并用 Nitro 建设了 33 个同源 BFF 路由。

项目最难的两条链路是阅读和支付。阅读侧需要处理加密正文、锁章、VIP、自动解锁、目录分页和章内续读；支付侧需要编排小说服务、支付服务和 PayPal，并在跨站回跳后恢复原章节上下文。

工程上，我把上游 JSON 当作不可信输入，通过运行时 guard 和 mapper 输出稳定领域模型，同时为正文 URL、支付跳转、敏感日志和 Long ID 精度做了专门防护。

目前大部分页面达到 BFF Ready，真实支付与线上正文样本仍有明确的 E2E 联调项。

## 一、架构、SSR 与 SEO

### 1. [核心] 公开内容 SSR、私有页面 CSR 的混合渲染矩阵

- 面试价值：公开书籍页保留首屏内容与 SEO；账户、阅读器、钱包、支付结果等个性化页面关闭 SSR。
- 技术抓手：Nuxt `routeRules` 按路由切换 SSR，并统一附加 `X-Robots-Tag`。
- 面试说法：我没有全站一刀切 SSR 或 SPA，而是根据页面是否公开、是否个性化、是否可索引来选择渲染模式。
- 代码证据：`nuxt.config.ts` 14–25、131–159 行。
- 适合岗位：前端 / 全栈 / 架构。

### 2. [核心] 书籍详情页完整 SEO 链路

- 面试价值：支持动态 title、description、canonical、Open Graph、Twitter Card、Book JSON-LD，并让 SSR 数据直接驱动元信息。
- 技术抓手：`useAsyncData` + `useSeoMeta` + `useHead`；服务端失败保留状态码；客户端带会话刷新个性化字段。
- 面试说法：我把内容 SEO 和个性化状态拆成 SSR 公共数据、挂载后带 Token 刷新两个阶段，爬虫和登录用户都能得到正确结果。
- 代码证据：`app/pages/book/[bookId].vue` 18–97 行。
- 适合岗位：前端 / SEO / 全栈。

### 3. [强辅助] 私有页面三层 noindex 防护

- 面试价值：`routeRules` 响应头、页面 robots meta、Nitro render hook 注入三处协同，降低 CSR 页面被误索引风险。
- 技术抓手：`X-Robots-Tag` + HTML meta + `robots.txt` disallow。
- 面试说法：私有页不能只靠 `robots.txt`，我在响应头和最终 HTML 中都做了 noindex，形成纵深防御。
- 代码证据：`server/plugins/noindex-html.ts` 3–31 行。
- 适合岗位：前端 / SEO / 全栈。

### 4. [强辅助] 页面层与业务域分离

- 面试价值：18 个路由页保持路由级职责，复杂 UI 和状态进入 account、book、commerce、discovery、reader、rewards、search 七个业务域。
- 技术抓手：pages 负责数据与 SEO，modules 负责 views/composables/types，shared 仅放跨域能力。
- 面试说法：我把 Nuxt 文件路由当作适配层，业务复杂度沉到领域模块，避免页面文件同时承担路由、状态和全部 UI。
- 代码证据：`README.md` 134–168 行。
- 适合岗位：前端 / 全栈。

### 5. [核心] SSR 同源请求封装与会话自动恢复

- 面试价值：SSR 继承请求上下文；accessToken 失效后只发起一次匿名会话恢复，并使用新 Token 重试原请求一次。
- 技术抓手：`useRequestFetch`、设备 Token header、single-flight Promise、错误码判定、有限重试。
- 面试说法：我把鉴权恢复做在同源请求边界上，并发鉴权失败不会创建多个匿名账户，写操作也不会无限自动重试。
- 代码证据：`app/composables/useApiFetch.ts` 19–102 行。
- 适合岗位：前端 / 全栈。

### 6. [强辅助] 面向 Amplify SSR 的运行时配置

- 面试价值：私有上游、支付、正文白名单与公开站点配置严格分层，处理构建期注入和字符串布尔值陷阱。
- 技术抓手：`runtimeConfig` private/public；显式使用 `=== 'true'`；开发和生产 dotenv 分离。
- 面试说法：我处理过 Serverless SSR 的真实部署约束，不是假设 `process.env` 在 Lambda 运行时随时可用。
- 代码证据：`nuxt.config.ts` 30–76 行。
- 适合岗位：全栈 / 工程化。

## 二、Nitro BFF、契约与安全

### 7. [核心] BFF 隔离上游与支付身份

- 面试价值：浏览器只访问 `/api/**`；上游 Base URL、签名盐、`firstPayToken` 等敏感信息只在服务端流转。
- 技术抓手：私有 `runtimeConfig`、Nitro handlers、支付 identity 内部模型、稳定响应裁剪。
- 面试说法：我把浏览器攻击面收敛到同源 BFF，支付 Token 不进入前端状态，也不会出现在 payment-options 响应中。
- 代码证据：`server/utils/payment-service.ts` 122–165、280–344 行。
- 适合岗位：全栈 / 后端 / 安全。

### 8. [核心] 统一上游签名网关

- 面试价值：所有小说请求自动注入 `tk/pkg/v/vn/lang/locale/ts/vc/os/vitaTaskFlg`，业务 handler 不重复拼装协议。
- 技术抓手：MD5 verification code、公共 query、可选 accessToken、单一请求出口。
- 面试说法：上游不是裸 REST，我把签名和设备协议收进 request gateway，新接接口只需要声明业务 path、query 和 body。
- 代码证据：`server/utils/novel-api.ts` 13–44、154–246 行。
- 适合岗位：全栈 / 后端。

### 9. [强辅助] SSR/CSR 共用稳定设备身份

- 面试价值：Header、Cookie、localStorage 三端对齐，SSR 首屏不会因无法访问 localStorage 而创建另一套匿名身份。
- 技术抓手：UUID、Cookie fallback、生产环境 `secure`、`SameSite=Lax`、客户端镜像。
- 面试说法：设备 ID 是跨 SSR/CSR 的一致性问题，我用 Cookie 做服务端锚点，用 Header 和 localStorage 保持客户端稳定。
- 代码证据：`server/utils/novel-api.ts` 131–151 行。
- 适合岗位：全栈 / 鉴权。

### 10. [核心] 契约优先的运行时 guard + mapper

- 面试价值：集中维护 DTO 断言和领域映射，未知 JSON 必须先校验，再进入前端领域模型。
- 技术抓手：TypeScript assertion functions、枚举收窄、必填/nullable 精确建模、DTO 到 domain mapping。
- 面试说法：TypeScript 类型不能保护运行时，我为上游响应增加 assert 和 mapper 双层处理，违约直接映射成带上下文的 502。
- 代码证据：`server/utils/dynamic-card-contract.ts` 36–165 行。
- 适合岗位：全栈 / 后端 / TypeScript。

### 11. [核心] 业务失败、契约失败、网络失败分层

- 面试价值：上游 HTTP 200 业务失败时保留 `messageInfo`；契约失败保持 502，同时保留真实上游 envelope 便于排查。
- 技术抓手：`rememberSuccessfulUpstream`、自定义 Nitro error handler、统一 API JSON 错误体。
- 面试说法：我没有把所有错误都吞成 500；用户提示需要业务码，开发排障需要原始 payload，两者在错误模型中同时保留。
- 代码证据：`server/error-handler.ts` 13–65 行。
- 适合岗位：全栈 / 后端 / 可观测性。

### 12. [核心] 章节正文安全代理

- 面试价值：避免浏览器直连密文 CDN，并防止上游内容 URL 被用于 SSRF。
- 技术抓手：精确 hostname allowlist、仅允许 HTTP(S)、禁止 redirect、10 秒超时、2MB 双重体积检查。
- 面试说法：正文 URL 虽由后端返回，我仍把它当作不可信输入，执行 host 白名单、禁止重定向、超时和体积限制。
- 代码证据：`server/utils/chapter-content.ts` 5–8、34–150 行。
- 适合岗位：全栈 / 后端 / 安全。

### 13. [核心] AES 解密后只输出安全段落

- 面试价值：服务端完成 AES-256-CBC 解密、JSON 结构校验、HTML 标签剥离、实体解码和常见英文标点乱码修复。
- 技术抓手：Node crypto、IV/key 长度校验、纯文本归一化、XSS 面收缩。
- 面试说法：我没有把解密后的远端 HTML 直接交给 `v-html`，而是在 BFF 归一化成 `paragraph[]`，将 XSS 风险留在服务端边界解决。
- 边界：仓库测试使用自造 crypto 向量，后端官方密文测试向量仍待联调。
- 代码证据：`server/utils/chapter-content.ts` 152–278 行。
- 适合岗位：全栈 / 后端 / 安全。

### 14. [核心] 支付出站 URL 与 SKU 二次校验

- 面试价值：下单前验证 SKU 属于当前场景；下单后只允许跳转 HTTPS `paypal.com` 或其子域。
- 技术抓手：服务端重新加载当前支付选项、decimal ID、hostname allowlist、HTTPS redirect base。
- 面试说法：我不信任浏览器传来的 `skuId`，也不信任支付中台返回的任意 URL，两个方向都在 BFF 重新校验。
- 代码证据：`server/utils/payment-contract.ts` 510–528、716–732 行。
- 适合岗位：全栈 / 支付 / 安全。

### 15. [强辅助] Long ID 全链路字符串化

- 面试价值：`userId`、`chapterId`、`payOrderId`、`psiId` 按十进制字符串传输，规避 JavaScript Number 安全整数丢精度。
- 技术抓手：decimal string guard、路由/query/body 类型统一。
- 面试说法：跨 Java 和 JavaScript 时，我主动识别了 int64 精度风险，把业务 ID 建模为字符串，而不是放宽为 `number | string`。
- 代码证据：`server/utils/payment-contract.ts` 140–143、514–554 行。
- 适合岗位：全栈 / TypeScript。

### 16. [强辅助] 可开关、递归脱敏的上游 tracing

- 面试价值：CloudWatch 可观察请求方向、服务、耗时和响应结构，但不会输出 Token、vc、credential、paymentToken。
- 技术抓手：运行时 debug gate、query/body/response 递归脱敏、8KB 截断、错误摘要。
- 面试说法：我把可观测性和安全一起设计：调试日志足够复现，但敏感字段会在任意嵌套层被 redact。
- 代码证据：`server/utils/upstream-debug.ts` 1–36、59–159、225–269 行。
- 适合岗位：全栈 / 后端 / SRE。

### 17. [加分] 不统一的上游分页被稳定化

- 面试价值：列表类空 result 映射为空数组，非空后再校验；对没有 `hasMore` 的接口使用 page-size fill heuristic 输出统一分页形状。
- 技术抓手：`readNovelApiResult` / `requireNovelApiResult` 分流、`{ records, hasMore }` 领域响应。
- 面试说法：BFF 不只是代理，它把 null、缺省和尾页语义翻译成前端统一的分页接口。
- 代码证据：`server/utils/novel-api.ts` 95–123 行。
- 适合岗位：全栈 / 后端。

## 三、阅读、支付与增长闭环

- 技术抓手：模块级 Promise、单一 session object、账户切换缓存隔离。
- 面试说法：我解决了并发匿名登录导致多个 Token、书架和余额串号的问题，账户切换时还会主动清理跨用户缓存。

### 19. [核心] 阅读器状态机覆盖免费、锁章、金币、VIP、Paywall

- 面试价值：同一阅读流处理目录、正文、VIP 免解、自动解锁、余额不足、付费墙、解锁后同步目录等状态。
- 技术抓手：computed gate mode、目录页缓存、request sequence、一次性自动解锁、防死循环集合。
- 面试说法：阅读器的难点不是渲染文本，而是权益状态机；我把锁章、VIP、余额和自动解锁收敛成可推导的 gate mode。
- 代码证据：`app/modules/reader/composables/useReader.ts` 123–238、282–356 行。

### 20. [强辅助] 分页目录缓存与邻接章节解析

- 面试价值：目录按页缓存；先估算目标页，再向两侧扫描，解决上一章或下一章可能不在当前页的问题。
- 技术抓手：Map page cache、estimated page、scan order、过期请求序列防覆盖。
- 面试说法：上游只给分页目录，我没有假设相邻章一定在同页，而是先命中估算页，再按距离补扫。
- 代码证据：`app/modules/reader/composables/useReader.ts` 211–238、358–388、504–560 行。

### 21. [核心] 本机章内阅读位置精确恢复

- 面试价值：按书保存章节号、段落索引、段内偏移比例和章末状态；进度只前进不回退，并兼容旧版数字存储。
- 技术抓手：localStorage schema migration、输入收窄、paragraph anchor、chapter-end sentinel。
- 面试说法：只存 `scrollTop` 在字号变化后会失真，我保存段落索引和段内比例，并单独建模章末推荐区。
- 代码证据：`app/modules/book/composables/useReadingProgress.ts` 14–39、114–218、220–369 行。
- 适合岗位：前端 / 阅读体验。

### 22. [强辅助] 阅读位置恢复的竞态治理

- 面试价值：换章先回顶并关闭 `overflow-anchor`；异步推荐到达后可再次钉住章末；过期 rAF 不能覆盖新章节位置。
- 技术抓手：restore generation、rAF、程序化恢复期间抑制回写、scroll anchoring 控制。
- 面试说法：阅读位置恢复不是简单设置 `scrollTop`，我处理了字号、异步推荐、换章 DOM 复用和过期动画回调。
- 代码证据：`app/modules/reader/views/ReaderView.vue` 648–920、1106–1185 行。
- 适合岗位：前端 / 性能 / 阅读体验。

### 23. [核心] 多上游 PayPal 支付编排

- 面试价值：一次加载支付选项串联用户身份、支付登录、渠道路由或推广策略、SKU 查询；Wallet、Membership、Paywall 共用。
