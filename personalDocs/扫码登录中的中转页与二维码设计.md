# 扫码登录中的中转页与二维码设计

## 概述

扫码登录里，二维码不应该直接承载登录凭证，而应该承载一个短期有效的一次性 `ticket`。中转页负责让二维码在系统相机、浏览器、App 内扫码器、iOS、Android 等不同环境下都有可处理路径。

推荐模型：

```text
二维码内容 = HTTPS 中转页链接 + 一次性 ticket
```

示例：

```text
https://auth.example.com/qr-login?ticket=QR_8f3a9c2d&client=web
```

## 中转页是什么

中转页是跨端桥接页面，不是最终业务页。它主要判断：

- 当前打开环境：微信、浏览器、系统相机、App 内扫码器
- 当前系统：iOS 或 Android
- App 是否已安装
- 二维码是否过期、已扫描、已确认或已取消
- 下一步应该唤起 App、展示网页、跳下载页，还是提示用户改用 App 扫码

在扫码登录场景里，中转页把 Web 登录页、移动端 App 和后端登录请求串起来。

## 二维码内容怎么选

| 方案 | 适用场景 | 主要问题 |
| --- | --- | --- |
| HTTPS 中转链接 | 扫码登录、营销页、下载页、跨端跳转 | 需要后端和 H5 中转页支持 |
| 纯业务字符串 | 只允许 App 内扫码器处理 | 系统相机扫了无法自然跳转 |
| 自定义 Scheme | 老项目或简单唤起 App | 可能被抢注，降级体验差 |
| Universal Link / App Link | 官方推荐的 App 唤起方式 | iOS / Android 都要配置域名关联 |

扫码登录优先使用 HTTPS 中转链接。纯字符串更像内部协议，安全边界清晰，但损失通用入口；自定义 Scheme 能唤起 App，但可靠性和安全性都不如基于 HTTPS 的官方方案。

## 推荐登录流程

### 1. Web 创建二维码

```http
POST /api/qr-login/create
```

后端创建登录请求：

```json
{
  "ticket": "QR_8f3a9c2d",
  "status": "WAITING_SCAN",
  "expireIn": 120,
  "qrUrl": "https://auth.example.com/qr-login?ticket=QR_8f3a9c2d"
}
```

后端需要保存 `ticket`、过期时间、Web 会话、状态和来源信息。

### 2. App 扫码并标记已扫

App 内扫码器识别二维码后，不直接登录，只提取 `ticket` 并请求后端：

```http
POST /api/qr-login/scan
Authorization: Bearer <App 登录态>

{
  "ticket": "QR_8f3a9c2d"
}
```

后端校验通过后，将状态改为 `SCANNED`。Web 端通过 WebSocket、SSE 或轮询展示“已扫码，请在手机上确认”。

### 3. App 展示确认页

确认页必须存在，不能扫码后自动登录。确认页应展示：

- 要登录的产品或系统
- 浏览器 / 设备信息
- 大致地点或 IP 风险信息
- 时间
- 确认和取消按钮

### 4. 用户确认后登录 Web

```http
POST /api/qr-login/confirm
Authorization: Bearer <App 登录态>

{
  "ticket": "QR_8f3a9c2d"
}
```

后端把 `ticket` 状态改为 `CONFIRMED`，把 Web 会话绑定到 App 当前用户，Web 端收到成功状态后进入系统。

## 建议的 ticket 状态机

比起只存一个布尔值，扫码登录更适合显式状态机：

```text
WAITING_SCAN
→ SCANNED
→ CONFIRMED
```

还需要处理终态：

```text
EXPIRED
CANCELLED
REJECTED
USED
```

关键约束：

- `ticket` 只能使用一次
- `ticket` 必须短时效，例如 2 分钟
- `CONFIRMED` 后不能再次确认
- `SCANNED` 后可允许同一用户短时间重复拉取确认页，但不能换用户确认
- Web 端登录态只能由服务端创建，不能由二维码直接携带

## 中转页的实际价值

中转页主要补齐四类能力：

- 通用入口：系统相机、浏览器、App 内扫码器都能识别 HTTPS
- 环境分发：iOS 走 Universal Links，Android 走 App Links，未安装则去下载页
- 安全前置：提前判断二维码是否过期、是否已使用、来源是否可信
- 降级体验：唤起失败、未安装、二维码过期时给用户明确反馈

没有中转页时，二维码一旦使用 `myapp://` 或纯字符串，系统相机、浏览器和未安装场景都会变得难处理。

## iOS 和 Android 注意点

### iOS

- 推荐使用 Universal Links，而不是只依赖自定义 Scheme
- 需要配置 Associated Domains
- 需要提供 `apple-app-site-association`
- App 要处理 Universal Link 回调
- App 内扫码需要配置 `NSCameraUsageDescription`

### Android

- 推荐使用 Android App Links
- 需要配置 `intent-filter`
- 需要提供 `assetlinks.json`
- Android 12 以后要重点测试已验证链接的打开行为
- App 内扫码需要声明并申请 Camera 权限

## App 内扫码 vs 系统相机扫码

| 入口 | 适合 | 不适合 |
| --- | --- | --- |
| App 内扫码 | 登录授权、后台管理系统登录、需要确认当前 App 用户身份的场景 | 纯营销下载链路 |
| 系统相机扫码 | 下载 App、打开网页、唤起 App 到活动页或商品页 | 作为扫码登录主路径 |

扫码登录优先 App 内扫码，因为 App 已经有当前用户登录态，可以做确认页、风控、设备校验和埋点。系统相机只能识别链接，不天然知道当前 App 用户是谁，因此更适合打开页面或唤起 App。

## 安全原则

不要在二维码中放：

- 用户登录 token
- 手机号
- 用户 ID + token
- 密码
- 长期有效的授权码

应该只放：

```text
一次性、短时效、随机、不可预测的 ticket
```

所有真正授权动作都走服务端校验。可以把 `ticket` 理解成临时排队号：它只标识“同一次登录请求”，不是身份证，也不是钥匙。

## 可补充的实现检查清单

- ticket 使用足够随机的 ID，避免可枚举
- 创建、扫描、确认都做频率限制
- Web 端轮询或长连接不返回敏感用户信息
- 确认页展示足够上下文，避免用户误授权
- 取消登录后状态进入 `CANCELLED`，不能再次确认
- 二维码过期后 Web 端要能刷新生成新 ticket
- 同一 ticket 被不同用户扫描时要明确拒绝或覆盖策略
- 服务端要校验 App 登录态，而不是相信扫码内容
- 日志中不要记录完整 token 或敏感参数
