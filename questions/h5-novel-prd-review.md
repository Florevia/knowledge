# H5 小说 Web 站 PRD 疑问与审查总结

## 1. 总体判断

当前 PRD 方向整体合理，核心目标是建设一个面向广告投放的 H5 小说站，打通从广告进站、匿名登录、阅读、锁章、支付、解锁到数据上报的转化链路。

但从前端视角看，当前一期范围偏大，已接近完整轻 App：包含阅读器、首页推荐、书架、任务奖励、用户中心、钱包、支付、账号体系、埋点和 CMS 配置等能力。建议先明确 MVP 范围，优先保证投放转化主链路可上线、可验证，再逐步迭代丰富模块。

## 2. 需求合理性审查

### 合理部分

- 匿名登录是必要能力，便于承接广告进站用户，并记录阅读进度、解锁状态、余额和归因信息。
- Reading Page、Paywall、Payment、Unlock Chapter 是项目核心链路，应作为首期重点。
- Paywall 根据 `psi` 或模板动态展示 SKU，符合投放场景下的差异化运营诉求。
- Meta Pixel、CAPI、悬壶等数据上报需求合理，有助于投放归因、转化分析和后续优化。
- Google 登录、Profile、Wallet、Transaction History 等能力有助于沉淀用户资产。

### 需要收敛或确认的部分

- 首期是否必须完整实现 `Library / Novel / Rewards / Profile` 四个 Tab，需要结合上线节奏评估。
- Rewards 任务体系会引入风控、重复领取、时区、刷量等问题，建议不要作为首期核心阻塞项。
- “点击 SKU 直接跳转 PayPal 支付”描述过粗，需要明确前端、后端、PayPal SDK、订单创建和支付回调的完整流程。
- “引导用户从 Facebook/Instagram 内置浏览器打开系统浏览器”只能作为引导能力，不宜承诺强制实现。
- Auto unlock 默认开启会影响用户付费感知，需要确认产品、法务和支付合规口径。

## 3. 前端实现难点

- 匿名用户与 Google 登录用户的身份合并规则复杂，需要明确资产迁移策略。
- 阅读器需要处理长章节渲染、章节切换、目录、锁章、阅读进度恢复、换行展示和弱网体验。
- Paywall 需要同时处理余额判断、自动解锁、SKU 展示、支付跳转、支付回调、权益刷新和重复点击防护。
- 支付成功不能只依赖前端状态，权益发放应以后端 PayPal capture 或 webhook 校验结果为准。
- 埋点需要统一封装公共参数、触发时机、去重规则、失败重试和调试能力。
- CMS 动态卡片需要稳定 schema，否则前端兜底逻辑会变得复杂且不可控。
- Facebook/Instagram 内置浏览器、移动端 Safari、Chrome、支付回跳和 Google 登录兼容性都需要重点测试。

## 4. 技术风险

- 支付链路风险：订单创建、支付成功、权益发放和异常补偿必须闭环。
- 归因链路风险：`pixelId / fbclid / campaign_id / adset_id / ad_id / bookid / psi` 的保存和传递规则需要明确。
- 数据一致性风险：阅读进度、余额、已解锁章节、自动解锁状态需要以后端数据为准。
- 合规风险：隐私政策、用户协议、账号删除、支付条款和 Auto unlock 说明需要在上线前确认。
- 投放环境风险：内置浏览器可能影响登录、支付、cookie、跳转和 Pixel 上报。
- 迭代风险：当前 PRD 涵盖模块较多，如果没有明确分期，前端交付和联调成本会快速上升。

## 5. 建议优先确认的问题

1. 首期 MVP 范围是什么？是否只保证广告进站到付费阅读闭环？
2. `psi` 的业务含义和粒度是什么？它与广告、书籍、SKU、模板之间是什么关系？
3. 匿名登录后再 Google 登录，阅读进度、余额、解锁章节、订单如何合并？
4. 付费模型到底按金币、章节、字数、VIP，还是多种并存？
5. Auto unlock 默认开启是否符合支付和用户告知要求？
6. PayPal 支付成功后，权益发放以同步 capture 为准，还是以后端 webhook 为准？
7. Meta Pixel 和 CAPI 的事件去重 ID 使用什么？是否统一使用订单号？
8. 动态卡片 CMS schema 谁负责定义？支持哪些卡片类型、图片比例和跳转目标？
9. 内置浏览器场景是否只做检测和引导，不承诺强制跳转系统浏览器？
10. 用户协议、隐私政策、Contact us 邮箱、账号删除策略是否已准备好？

## 6. 建议分期

### 第一阶段：核心闭环

完成广告进站、匿名登录、Reading Page、Chapter List、Paywall、PayPal 支付、章节解锁、基础 Profile 和关键埋点，保证项目可上线、可投放、可验证。

### 第二阶段：用户与运营能力

补齐 Novel、Library、Rewards、Wallet、Transaction History、Settings、搜索、推荐卡片等模块，支持用户沉淀和运营增长。

### 第三阶段：持续优化

根据投放数据和用户行为，持续优化阅读体验、付费转化、Paywall 模板、推荐策略、性能体验和多端兼容性。
