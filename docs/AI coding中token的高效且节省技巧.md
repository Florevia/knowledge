AI coding中token的高效且节省技巧
一、为什么要关注 Token
Token 成本到底花在哪里？

计费上通常拆成三类（API 响应里的 `usage` 字段）：

| 类型 | 含义 | 典型单价（相对） |
| --- | --- | --- |
| 输入 token | 本轮新处理、未命中缓存的上下文 | 基准价 |
| 缓存写入 token | 首次把某段前缀写入 KV cache | Anthropic 约 1.25× 输入价；OpenAI 无额外写溢价 |
| 缓存读取 token | 与上一轮前缀逐字节匹配的重用部分 | Anthropic 约 0.1×；OpenAI 约 0.5× |
| 输出 token | 模型生成内容 | 通常高于输入，且无法缓存 |

> **总成本 ≈ 未缓存输入 + 缓存写入 + 缓存读取 + 输出**  
> 多轮 Agent 里，Prompt Caching 让稳定前缀（系统提示、工具定义、项目规则）在后续轮次按缓存价计费。

**输入 Token 包括：**

- **System Prompt**：产品内置指令、输出格式、安全策略。
- **工具 / MCP 定义**：每个工具的 JSON Schema；多开 MCP 时可达数万 token，且**每轮请求都会带上**
- **项目常驻上下文**：`CLAUDE.md`、`.cursor/rules`、`AGENTS.md` 等
- **历史对话**：用户消息、模型回复、**历次工具调用的参数与返回**。
- **用户当前问题**
- **RAG / 检索结果**
- **文件 / 图片 / 代码上下文**
- **多轮 Agent 中间过程**：搜索命中、终端输出、测试日志等

**输出 Token 包括：**

- 模型回答
- Markdown / JSON / **完整文件**（往往比 diff 贵一个数量级）
- 工具调用说明、结构化参数
- Extended thinking / 推理过程（若开启）

**一次 Agent 任务里，token 大致花在哪：**

| 开销来源 | 占比（约） | 说明 |
| --- | --- | --- |
| 工具与终端输出 | 15%～25% | 测试日志、CLI 输出；几十次 `run` 即可累积数十万 token |
| **上下文重复发送** | 15%～20% | 每轮 API 重发**整段**历史；第 50 轮比第 1 轮贵一个数量级 |
| 推理 / 规划 | 10%～15% | 必要，但会随上下文变大而变贵 |
| **代码生成** | 5%～15% | 往往反而是最便宜的一块 |
| 搜索 / 读文件探索 | 余下部分 | 与任务边界是否清晰强相关 |

复杂 Agent 任务（如 SWE-bench 风格修复）整体可达 **百万～数百万 token/任务**（含重试与自纠错）；长会话在启用缓存时，**输入侧 90%+ 可能已是缓存命中**，仅尾部新内容按全价计。

**真正昂贵的是多轮循环：** 一次 AI coding 通常会经历搜索 → 读文件 → 修改 → 跑测试 → 修复 → 复查。模型**不会**在轮次之间记住任何东西，因此**每一轮**都会把：系统提示 + 工具表 + 项目规则 + **至今全部对话与工具结果** + 新消息，再发一遍。

Morph 等实测：会话从每轮约 5K token 膨胀到 **200K token/轮** 并不罕见；Claude Code 在缓存命中良好时，长会话可把输入侧成本压到约 **1/5～1/8**（官方称会监控 cache hit rate，并将其视为成本与延迟的核心指标）。

**Token 浪费的典型场景**

- 整仓扫描、把整段 CI 日志贴进对话（应给路径 + 关键行，让 Agent 自己读文件）
- 问题边界不清，Agent 盲目探索无关目录
- 每轮重复口述项目背景、需求与约束（应沉淀进 `CLAUDE.md` / Rules）
- 让 AI 输出**完整文件**，而不是修改点或 diff
- 长会话不 `/clear` 或 `/compact`（无关任务仍背着旧工具输出）
- 把动态内容（日期、分支名、随机数）写进 **Always Apply** 规则，破坏 prompt cache
- 无必要地挂载大量 MCP，或 Agent Team 多实例并行（每个 teammate 独立上下文，token 约按人数倍增）


二、Prompt 层面的优化
把 Prompt 写短，但写准
原则：缩小范围 -&gt; 明确目标 -&gt; 限制输出 -&gt; 允许执行。
推荐模板：
目标：修复 xxx 问题。
范围：只看 src/modules/xxx 和相关 API，不做无关重构。
现象：xxx 操作后出现 xxx。
验收：xxx 测试通过，且页面 xxx 行为正常。
输出：先说明改动计划，再改代码，最后给验证结果。
明确输出格式，减少无效输出
只读分析：要求输出“结论、证据、风险、下一步”。
写代码：要求输出“改了什么、为什么、如何验证”。
Debug：要求输出“假设、证据、验证命令、结果”。
Code review：要求按严重程度列问题，不要泛泛总结。
代码任务优先输出 diff，而不是完整文件
企业代码库里，完整文件输出往往包含大量未变化内容。更省 token 的方式是让 AI 只说明修改点，并直接应用补丁：
小改动：指定文件和函数，让 AI 直接改。
中等改动：先让 AI 给计划，再分批改。
大改动：先拆任务，不要一次性让 Agent 横扫全仓。
Rules 要短、分层、按需触发
Cursor 的 Rules 会作为持久上下文注入到模型上下文中；规则可以放在 \.cursor/rules，支持按项目、路径、相关性等方式应用。
但Rules 太长会导致每次请求消耗额外的token，推荐 拆成小规则，例如：
.cursor/rules/
  frontend-style.mdc
  react-component.mdc
  api-client.mdc
  testing.mdc
示例：\.cursor/rules/react-component.mdc``
description: React component conventions
globs:
  - "src/components/***/**.tsx"
  - "src/pages/***/**.tsx"
alwaysApply: false
---
- 使用 React 函数组件和 TypeScript。
- Props 必须显式声明类型。
- 避免 any。
- 样式优先使用 Tailwind CSS。
- 不要引入新的状态管理库，除非用户明确要求。
关键点：能不用 Always 就不用 Always。否则每次对话都会带上这段规则。
> alwaysApply: false 不是「关掉这条规则」，而是 「不要每次对话都强制带上」；需要时仍会通过 路径匹配、任务相关性、主动引用 等方式注入。

三、上下文管理
按需加载，而不是预加载
好的上下文不是“越多越好”，而是“刚好够用”。这类问题称为 context engineering：核心不是塞入更多上下文，而是在有限注意力预算里放入最小且高信号的信息。
✅ 实践方法：
给 AI 文件路径、函数名、错误信息，而不是整段无关代码。
让 AI 先搜索和阅读相关片段，再决定是否继续扩展范围。
对日志只给关键错误、复现步骤、最近几十行；必要时让 AI 自己读取完整日志。
把中间结果放在文件、终端、CI、issue 中，聊天里只保留结论和证据。
沉淀稳定规则
重复出现的规范不要每次手打，放到Agents说明里：
AGENTS\.md：多 Agent 通用规则、构建命令、测试命令、代码边界。
\.github/copilot\-instructions\.md：GitHub Copilot 仓库级规则。
\.github/instructions/\*\.instructions\.md：按路径或技术栈生效的局部规则。
官方文档也建议把构建、测试、架构布局等稳定信息写进自定义指令，减少 Agent 每次重复搜索。
包管理器与已验证的安装/构建/测试/lint 命令（含失败时的 workaround）
目录地图：入口、配置、测试放哪
不可违反的边界（禁改目录、禁新依赖、安全要求）
输出偏好（优先 diff、先 plan 再改）
CI/PR 前必跑项
及时开新会话
❗️ 两个原因：
每次发消息，模型收到的上下文大致包括：
系统提示、Rules、工具定义
整段对话历史（你的问题、AI 回答、读过的文件片段、终端输出）
本轮@的文件、需求、报错等
这些加起来占满 context window。窗口满了之后：
截断最前面的内容（直接丢信息）
摘要压缩旧对话（保留大意、丢细节）
单上下文原则（ Single Context ，cursor团队分享的思路），在一段对话里理解两个以上的目标，会出现：
改错文件、改多余文件 （对话历史遗留上个任务的文件和假设）
越聊越啰嗦、越跑题 （之前话题挤占注意力）
✅ 推荐：
> AI 编码的瓶颈 increasingly 是 context，不是模型智商。
> 一个 session 只做一件事 → 减少噪声和误改；切换任务就新开 → 不付上一任务的 token 税；长任务主动摘要 → 在爆窗前保留「目标、文件、决策、测试」，而不是保留「读了哪些无关目录」。
> 
> 
长期上下文和临时上下文
✅ 长期上下文：适合放到项目规则、团队知识库、固定 prompt 里。
类型	示例
产品定位	服务谁，解决什么问题
技术展	前端、后端、数据库、部署方式
代码规范	命名、目录、接口返回格式
品牌语气	文案风格、禁用词
业务规划	权限、价格、流程、合规要求
核心指标	转化率、留存、付费率等
> 长期上下文不应该每次都发送
> 
> 
✅ 临时上下文：每次任务单独提供
类型	示例
当前bug	那个页面、什么操作、报什么错
当前需求	这轮要设计哪个功能
当前活动	活动目标、周期、预算
当前数据	本次实验数据、用户反馈
当前约束	不能改什么、必须保留什么
> 临时上下文要精简、准确，只围绕当前任务
> 
> 
长任务要做检查点
长任务每完成一个阶段，让 AI 产出短检查点：
当前目标：
已改文件：
关键决策：
验证结果：
遗留风险：
下一步：
这样后续继续任务时，可以用一段高信号摘要替代完整历史。
复杂任务业务逻辑：每次更改同步更新文档

**原理**

业务逻辑重的模块（定价、权限、审批流、活动规则、结算等），真实规则往往散落在多文件、多分支和注释里，代码只是「可执行副本」，不是最易读的说明。

需求迭代时，若只让 Agent 从仓库反推规则，典型路径是：搜索关键词 → 读多个 service/handler → 追调用链 → 对照测试与配置 → 再改代码。每一轮改动都会重复这条链路，**同一段业务上下文会被多次读入对话**，输入 token 随轮次线性甚至叠加增长。

相反，一份与代码同步、按领域拆分的业务说明，是把「读仓库」压缩成「读摘要」：**用几百字的文档，替代成千上万行代码的扫描成本**。文档是给人和模型共用的高信号上下文，符合 context engineering 里「最小且高信号」的原则。

**实现**

1. **写什么（按领域，不写实现细节）**
   - 业务目标与边界：谁、在什么场景、能做什么 / 不能做什么。
   - 核心规则与优先级：判断顺序、例外、互斥关系（用表格或编号列表）。
   - 状态与流转：状态机、触发条件、副作用（写库、发消息、记账）。
   - 与外部系统的约定：依赖哪些配置、开关、枚举；变更时要动哪些表/接口。
   - 变更记录（可选）：日期 + 一句话「改了什么、为什么」，便于 diff 式阅读。

2. **放哪、怎么用**
   - 与模块同目录或 `docs/business/`：`docs/business/pricing.md`、`src/modules/order/ORDER_RULES.md`。
   - 在 `AGENTS.md` 或 `.cursor/rules` 里加一行索引：「改订单/定价前先读 xxx.md」，**按需 @ 引用**，不要写进 `alwaysApply` 长规则。
   - Prompt 模板固定一句：`业务规则以 @docs/business/xxx.md 为准；代码仅作实现参考，冲突以文档为准并指出差异。`

3. **何时更新（与代码同 PR）**
   - 规则、状态、枚举、对外行为任一变化 → **同一 PR 内改文档**，和单测一样视为交付物。
   - Code review 检查项：逻辑变了吗？对应业务文档更新了吗？
   - 大重构前：可先让 Agent **只读**文档输出「影响面清单」，再动代码，避免先扫全仓再规划。

4. **文档形态（省 token）**
   - 单篇控制在可一次 @ 读完（通常 1～3 屏）；过长则按子域拆分，用目录互链。
   - 避免粘贴大段代码；用「见 `XxxService#calculate`」指针即可。
   - 用「规则 ID + 一句话」代替散文，方便在 prompt 里引用：`R3：未支付订单 30 分钟内可取消`。

**效果**

| 维度 | 只扫仓库 | 文档 + 按需读代码 |
|------|----------|-------------------|
| 输入 token | 每轮重复读多文件、多轮搜索 | 首轮 @ 文档即可建立心智模型 |
| 迭代轮次 | 易漏分支/历史特例，反复求证 | 规则集中，改前对齐文档 |
| 准确性 | 易把旧注释、死代码当真相 | 文档与 PR 同步，显式标冲突 |
| 协作 | 新人/Agent 都要重新「考古」 | 同一套业务真相，可复用检查点 |

典型收益：**复杂需求从「每轮全链路扫仓」变为「文档定锚 + 只读改动点」**；Agent 只在实现/验证阶段打开相关文件，探索性搜索次数明显下降。团队侧则把隐性知识外显，减少「只有老员工知道」导致的重复问答 token。

> 一句话：**代码负责正确执行，文档负责正确理解；业务越重，文档越要跟着改，比让模型一遍遍读仓库更省 token、也更稳。**

四、缓存与模型调用策略
稳定前缀，动态内容后置
✅ 背景：
利用 prompt caching 的特点：
（很多模型/API（OpenAI、Anthropic 等）会对请求的前缀做缓存：
> - 请求开头有一段完全相同的内容（系统提示、工具定义、仓库规则等）→ 可以复用上次算过的结果，便宜、也快。
> 
> - 前缀里哪怕差一个字（多一个时间戳、换一行状态）→ 整段前缀算“变了”，缓存失效，按全新输入计费/计算。
> 
> 官方文档的核心就是：静态内容放前面，变量内容放后面
> 
> 
对企业研发的含义：
不要频繁改系统提示词、工具定义、全局规则。
不要把当前时间、临时状态、用户输入塞进常驻前缀。
工具列表和 schema 尽量保持稳定顺序。
API 集成要观察 cached\_tokens、cache\_read\_input\_tokens 等指标，不要凭感觉优化。
小任务用小模型，大任务用强模型
小模型：命名、格式化、简单脚本、局部解释、日志摘要。
强模型：跨模块重构、复杂 bug、架构方案、风险评审、安全相关变更。
混合策略：让便宜模型做搜索和摘要，让强模型做最终判断和关键修改。
五、模式选择：先省探索成本，再省返工成本
Ask 模式：只读分析
适合“弄清楚”：查调用链、解释模块、定位可能原因。它最省，因为不会引入修改和验证循环。
Plan 模式：复杂任务先规划
适合跨文件、跨模块、有多种实现路径的任务。先规划能减少 Agent 盲改和返工。
Agent 模式：让 AI 动手，但必须给边界
适合目标明确、验收明确的改动。关键是给出边界：允许改哪些文件、不能做什么、验证命令是什么。
六、企业团队可执行清单
每个任务先写清：目标、范围、验收、测试命令。
日志只给关键片段；大文件让 AI 自己按需读取。
仓库规则写进 AGENTS\.md 或 Copilot instructions，不在每次对话里重复。
复杂任务先 Plan，再 Agent；小问题直接 Ask 或局部 Agent。
长任务定期生成检查点，用摘要替代完整历史。
API 场景优先利用 prompt caching，并监控缓存命中指标。
代码输出优先 patch/diff，少输出完整文件。
